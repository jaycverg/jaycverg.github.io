Rules Graduate Downward

Prose, then memory, then a check that refuses — and what happens when the check has bugs too.

November 6, 2026 8 min read Claude Code · Hooks · Guardrails

My Claude Code settings live in a dotfiles repo. ~/.claude/settings.json is a symlink into that checkout, so every change is a git diff, and my two machines share one config.

On October 7, I noticed it wasn't a symlink anymore. It was a regular file with the right contents, sitting where the link used to be. Every change from then on would have stayed on that one machine and never reached the repo — and nothing would have said a word.

It wasn't the first time. There was a backup in the Trash from two weeks earlier that looked a lot like the same thing, and nobody had traced it. This time I asked Claude to.

The culprit was Claude

The diagnosis took a few minutes. First, cmp confirmed the stray file matched the repo copy byte for byte, so nothing was lost. Then the link went back. Then Claude searched my past session transcripts for the command that had touched the file, and found it — in another Claude session, a few minutes earlier, where I'd asked it to turn on a setting:

F="$HOME/.claude/settings.json"
jq '.someSetting = true' "$F" > "$F.tmp" && mv "$F.tmp" "$F"

The command, with the setting name replaced.

That's the textbook atomic write: render to a temp file, then rename over the original so nothing ever sees a half-written file. It's exactly what you'd want — unless the original is a symlink. mv onto a link replaces the link itself. The repo copy is left behind, and the live config is now an untracked file that looks completely normal.

I had a hook guarding writes into the config directory. It didn't fire, because it only matched a literal path, and here the path was in a variable.

Then Claude said the thing that this post is about:

"Your rule is that something violated twice should become a check that fails."

The ladder

That rule is in my global instructions file, and the rest of this series keeps coming back to it:

Rules graduate downward, and the ladder only goes one way:
prose → memory → a hook or lint check. A rule violated twice should
become something that fails, not a sentence someone has to remember.
When you notice that, say so and propose the check; don't add a third
paragraph of prose.

Source: my global Claude Code instructions file, verbatim.

Each step down is harder to ignore and costs more to build — with one wrinkle in the middle:

  • Prose — a line in an instructions file. Cheap to write, loaded into every session and followed most of the time. "Most of the time" is the problem.
  • Memory — a correction Claude saved after I made it. It's recalled when something makes it relevant, which means it's also not recalled when nothing does. So it's a holding pen more than a rung: a correction lands there first, then goes into the file it corrects — or, if it keeps getting broken, becomes a check. More on that in the next post.
  • A hook or lint check — code that runs before the tool call and refuses the bad one. It doesn't depend on the model remembering anything.

The important word is twice. Once is a mistake, and a sentence is the right-sized fix. Twice means the sentence isn't working, and a third paragraph of prose won't either.

Building the check

I asked for a hook rule refusing mv and cp onto a symlinked path in the config directory. Claude pushed back on half of that — after testing what each command actually does to a link, rather than going on what I'd said:

Replaces the link (refuse)Writes through it (allow)
mvplain cp, cp -f
cp --remove-destinationsed -i --follow-symlinks
installshell redirect, > link
sed -i

Source: behavior measured in the session that built the rule, before the rule was written.

Plain cp writes through a symlink; refusing it would have blocked a perfectly safe command. Meanwhile sed -i and install — which I hadn't thought of — both replace the link, and went into the rule. The rule also resolves ~, $HOME and a variable assigned earlier in the same command — the exact case that got past the old guard.

/**
 * Refuse a write that would REPLACE a symlink in the Claude config dir
 * with a regular file. `mv` onto a link replaces the link: the live
 * settings became an untracked regular file and every later edit
 * stopped reaching the repo, with nothing to say so.
 */
function denyConfigSymlinkReplace(stage) {
  for (const { word, file } of linkReplacingWrites(stage)) {
    if (!file || !inConfigDir(file) || !isSymlink(file)) continue;
    deny(`Writing onto ${word} would replace a symlink with a regular ` +
         `file. It links to ${fs.realpathSync(file)}, so the change ` +
         `would silently stop syncing. Write to the link's target.`);
  }
}

Source: the rule as committed to my dotfiles repo, trimmed and simplified.

Note the refusal message. A hook's deny text is read by the model, so it's an instruction too: it says what went wrong and what to do instead. A bare "denied" just invites the model to try the same thing a different way.

The rule shipped with a probe script in the spirit of the last post: commands that must be refused and commands that must still pass, now part of the hook's test suite. About a week later, a third layer joined it — the startup check that compares my machine against the repo now also verifies that settings.json is still a link.

Hooks have bugs too

The day after, I ran /retro — a command that goes back over recent sessions looking for mistakes worth turning into fixes. It found something worse than a symlink.

A subagent had issued a write command split across two lines with a backslash, and it had sailed through without the approval prompt it should have triggered. That looked like a one-off. It wasn't.

The hook's parser turned every newline into a command separator before it looked at anything. So a backslash-continued command — which the shell reads as one line — reached the hook as two fragments, and the verb, the flag or the argument that a rule was looking for was no longer where the rule looked. When Claude re-ran the whole probe suite with a continuation spliced after each command's first word, about 270 verdicts flipped, including roughly 110 commands that should have been refused and went through, and about 70 that should have asked first and didn't. Thirteen separate rules were blind to it.

A guard is code. It has bugs, it needs tests, and its tests need to include the inputs an adversarial — or merely creative — caller would try.

The first fix tried to join continuations the way the shell does, and closed all thirteen. It also opened nine new holes — comments after a ;, command substitutions inside double quotes, a couple of heredoc shapes — wherever its join disagreed with the shell's. An independent reviewer found them over several rounds of review.

The version that shipped kept the smarter parser but stopped trusting it on its own. The command is judged under three readings — the old parser's exact reading (the version on master), the text as typed and the text with continuations joined — and the strictest verdict wins:

// Three readings, every verdict unioned. The FIRST is master's, byte for
// byte: it is the floor, so a parse that is smarter than master's can
// only add a deny or an ask.

Source: the comment above the check in the hook, trimmed.

And a new probe replays every command in the suite through both the old hook and the new one, failing if the new one is ever more permissive. It went RED against the broken intermediate version. That probe is the actual fix; the parser change is just what made it pass.

When a hook is the wrong rung

Hooks are the strongest rung, which makes them tempting for everything. A config audit I'd run about a week before the symlink incident pushed back on that, and its summary is worth quoting:

"The layer is worth keeping for exactly one thing — an ask on outward writes, secret reads and deletions, which no plugin or classifier can be configured to give — and is actively harmful in two of its other roles."

The argument: if a rule is just a name pattern — "ask before any tool whose name starts with create" — the settings file's own permission rules already express it, with native "always allow for this session" handling. A hook is for what settings can't say: splitting a compound command into its parts, resolving where a path really points, rewriting a shell idiom that's known to misbehave. One deny family I'd written for scary commands had fired zero times in thirty days of logs.

I'll be honest about how that went: the audit said shrink the hook, and the hook has more than doubled since, mostly with fixes like the two in this post. Some of that is the audit being right and me not acting on it. Some of it is that the cases a name pattern can't express keep turning out to be the ones that matter.

The one I push by hand

One more hook, because it shows the bottom rung doing a job prose couldn't. My instructions tell Claude to confirm the target branch before pushing. That was prose, and it was followed. Then I noticed my push hook had an allowlist that meant allow silently, which made the prose rule impossible to enforce.

Now the allowlist decides how a push is gated, not whether: a branch I've listed gets a confirmation prompt; anything else — the main branch by default, remote deletes, mirror pushes — is refused outright. Even when I'm the one asking. Recently I told a session to push my dotfiles to master, and got this:

🚫 Push blocked — push this one by hand.
Reason: branch 'master' is not allowlisted.
Do not retry this push in another form. Print the exact command
for the user to run.

The hook's refusal, trimmed.

Claude said nothing had been pushed, printed the command, and I ran it myself. It costs me ten seconds. That's cheap for making sure no session — no matter how confident, or how creatively it parses my request — pushes to master on its own.

What goes where

After a few months of this, my rough sorting rule:

  • Judgment stays in prose. "Match the register to the reader" can't be a regex.
  • Corrections go to memory, briefly — and then into the file they correct.
  • Anything violated twice that a machine can check becomes a check. With a probe that fails without it.
  • Name patterns go to settings; only what settings can't express goes in a hook.

Rules only go down. I haven't yet taken a hook out and replaced it with a sentence — and I don't expect to.
