Unit Tests for Prompts

RED/GREEN probes with a fresh reader — because re-reading what you just wrote proves only that you wrote it.

October 25, 2026 8 min read Claude Code · Prompt engineering · Testing

In the last post, the second-biggest row in my month of Claude Code sessions had nobody at the keyboard. It was 103 headless sessions whose whole job was to read one of my instruction files cold and tell me what they'd do. Add the hundred subagents that did the same job inside other sessions, and it's the job Claude does for me more often than any other.

This post is about why. The short version: I kept changing a skill, reading it back, deciding it was clear — and watching a fresh session do the wrong thing anyway.

Re-reading proves the write succeeded

A skill, a slash command, an agent definition, an instructions file: none of them have unit tests. Their "behavior" is whatever a model does after reading them. So the default way to verify a change is to read the file again and decide it says what you meant.

That check is close to worthless, for the same reason proofreading your own writing is. You know what you meant. You read the sentence you intended, not the one on the page. And if you ask the same Claude session that made the edit, it's worse: that session already holds the old text in its context, has been told what the new text is for and will cheerfully confirm it.

My skill for this opens by saying exactly that:

Prompt-shaped changes have no unit test. The failure mode is that they get "verified" by re-reading the file that was just written, which proves only that the write succeeded.

The fix is the same one test-driven development uses for code. Make the test fail first, then change the thing, then make the test pass — with a reader that has never seen the conversation.

The loop

Every edit to a prompt-shaped file in my setup goes through a skill called probe-changes. It has four steps.

1. Commit first

A safe point, before touching anything. This sounds obvious until you notice that most agent config lives behind symlinks into a dotfiles repo, so the directory you're editing in often isn't the repo that holds the file. The skill resolves the real path and insists it's clean before the edit — otherwise the git checkout meant to rescue a bad edit also destroys the good, uncommitted one before it.

2. Write the probe, and prove it RED

A probe is a fixed scenario plus the behavior you expect after the change. You run it against the current file first and record the wrong answer. That recording is the RED.

If you can't make it fail on the current version, one of two things is true: the probe is wrong, or the change is unnecessary. Either is worth knowing before you edit. A probe that passes on both old and new proves nothing — it's a test that can't fail.

3. Prove GREEN somewhere that actually reloads the file

This is the step that's easiest to get wrong without noticing. Where the GREEN run happens depends on when the file is read:

What you changedRead whenWhere a real GREEN runs
A skill or slash commandEach time it's invokedA subagent, or a fresh invocation
An agent definitionEach time the agent spawnsThe next spawn of that agent
The instructions file, settings, hooksOnce, at session startA brand-new session
A prompt inside application codeAt process start or deployThe running deployment

Source: the reload table in my probe-changes skill, lightly reworded, one row omitted.

The rule behind it: anything loaded once per session needs a new session. A subagent inherits its parent's already-loaded copy and will happily confirm the old behavior. When in doubt, start a new session — it's strictly safer and costs a few seconds.

4. Probe what must not change

Two or three probes over neighboring behavior, before and after. Prompt edits break the behavior next to them far more often than the behavior you edited: sharpening one instruction routinely mutes the one next to it. Same bar as code — zero new failures, measured, not assumed.

The fresh reader

For anything read per invocation, the fresh reader is a dedicated agent. Its definition is short, and most of it is about what it must not do:

---
name: probe-runner
description: "Fresh-reader probe for per-invocation prompt files:
  reads the given files and reports what it WOULD do in a scenario —
  decision, tool calls, governing line — without executing anything."
tools: Read, Grep, Glob
---

- Simulate; never execute.
- Do not fill gaps with good judgment. If the files do not say what
  to do, the answer is "unspecified", followed by what you would
  default to.
- Quote, don't paraphrase. The governing line is copied verbatim
  with its filename.

Source: my probe-runner agent definition, trimmed. The full file also pins a model and caps its turns.

Two lines in there do most of the work.

"Do not fill gaps with good judgment." A capable model reading an incomplete instruction will usually do something sensible anyway. That's great in production and useless in a test: the sensible guess hides exactly the gap you're looking for. A probe runner that says "unspecified — I'd default to X" has found a bug. One that silently does X has buried it.

"Quote, don't paraphrase." Every answer names the sentence that produced it. When a probe comes back wrong, I don't have to guess which line misled it — it tells me, and that's usually the line I edit.

Its answer comes back in a fixed shape:

1. <scenario>
   Decision: <what it would do>
   Calls:    <each tool call it would make, with key parameters>
   Governing line: <file> — "<verbatim sentence>"   (or: unspecified)
   Conflicts / gaps: <none | what the files leave open>

Source: the answer format in my probe-runner agent definition, reworded.

The probe that passed before I made the change

Here's the failure that taught me the most.

My instructions say anything I ask Claude to delete goes to the Trash, never rm — and a hook refuses rm outside temp directories, so it isn't optional. That's the right default for almost everything: untracked work exists in exactly one place, and the Trash makes a mistake recoverable.

Except for one kind of file. A file holding a live credential — an API token, a .env with real keys — should not be recoverable. The Trash is a browsable, persistent copy sitting outside whatever protection the original location had. For a secret, recoverability is the threat.

I'd already corrected Claude on this once, and the correction lived in its memory. Now I wanted it in the instructions file proper. So I wrote the probe — "I ask you to delete a file that holds a live token; what do you do?" — and ran it against the unedited file, expecting RED: "move it to the Trash."

It came back GREEN. Shred it in place, don't trash it, and rotate the token.

Nothing was wrong with the probe. A fresh session loads memory too; this one recalled my earlier correction and answered from that. The probe was testing the memory, not the file. If I'd taken that GREEN at face value, I'd have shipped an edit I never proved did anything.

The fix is now a paragraph in the skill: when an edit absorbs a memory, run both RED and GREEN with memory switched off.

CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude -p "Scenario: I ask you to delete
.local/tmp/deploy.env. It holds a live API token. From your standing
instructions only, in 3–6 sentences: what do you do? DO NOT call any
tool — name the first call you would make."

The shape of the probe, reconstructed for this post — the original scenario named a different file.

With memory off, the unedited file gave the RED I expected: trash the file. After the edit, the GREEN: shred it, truncate it and tell me the token still needs rotating wherever it leaked from. Because this was the instructions file — read once at session start — the GREEN had to run in a brand-new session, not a subagent.

And note what the skill says not to do: don't get the clean RED by moving the memory file aside. My memory store is shared and tracked in git. A moved file disappears for every other session using it.

Designing a good scenario

After a hundred-odd of these, a few patterns keep showing up in the probes that actually catch things:

  • "From your standing instructions only." Otherwise the model reasons its way to a good answer from first principles, which tells you about the model, not the file.
  • "DO NOT call any tool — name the first call you would make." The first tool call is the routing decision. Did it reach for the right skill, the right agent, the right command? That's often the whole test, and it's cheaper than letting the session run.
  • A length budget, like "3–6 sentences." Long answers hedge. Short answers commit.
  • Assert properties, not wording. Did it refuse? Was the required section there? Was the expected tool called? Exact-string checks on model output are flaky by construction.
  • Run a borderline probe two or three times before believing either color. And if a RED can't be explained, it stops the work — it doesn't get re-run until it happens to come back green.
  • Pin the model. If the skill runs on one model in real use, probe it on that model. A GREEN on a different model says nothing about how the file behaves on the model it actually runs on.

The transcript is the result

"It reads better now" is not evidence. The before and after probe transcripts are, and they go in the pull request description, where a reviewer can see what the change actually did to behavior. Probes worth keeping become scripts next to the file they test, so the next edit starts with a small suite instead of a blank page.

It's more ceremony than editing a Markdown file feels like it deserves. But these files steer every session I run. A wrong sentence in one is a bug that fires every time it's read, and the only way I've found to catch that is to let something read it that doesn't already know what I meant.
